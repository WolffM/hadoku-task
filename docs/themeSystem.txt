# Advanced Themes — Audit & Productionization Plan

A read of where "advanced themes" lives across the workspace, what's
inconsistent, and a plan to make it shippable as part of
`@wolffm/themes` so any consumer (hadoku-task, hadoku-site, third
parties) gets it for free.

---

## 1. The vision (restated)

`@wolffm/themes` ships **18 base themes** (9 families × light/dark).
Some of those themes have an **advanced visual contract** — a
gradient, animated effects, and optional color overrides — defined
**inside their own theme block**, not as a separately-named package.
A theme like `light` IS its advanced identity; there is no
`beach-day`. Whether the advanced visuals render is controlled by a
single `themeMode` preference (`'simple' | 'advanced'`). When the
active theme has no advanced contract, the toggle is hidden.

The editor (`themes/dev/editor.html`) is a consumer of the published
package — same imports, same attributes, same hooks. What you tune
is what you ship.

---

## 2. Where each piece lives today

| Concern | Location | Status |
|---|---|---|
| Base theme tokens (18 themes) | `themes/src/style.css` | ✅ shipped in package |
| Advanced gradient stop tokens (light only) | `themes/src/style.css` lines 61–85 | ⚠️ in package but isolated to `[data-theme='light']` |
| Advanced **theme block** (gradient assembly, effects, simple-mode override) | `src/styles/advanced-themes.css` (consumer) | ❌ **not in the package** |
| `ADVANCED_THEME_MAP` (`light` → `beach-day`) | `src/app/themeConfig.tsx` AND `themes/dev/config.js` | ❌ duplicated; collapsing the naming kills it entirely |
| `data-advanced-theme` attribute setter | `src/hooks/useTheme.ts` AND `themes/dev/editor.js` | ❌ duplicated; replaced by `data-theme-mode` |
| `data-simple-mode` attribute setter | `src/hooks/useTheme.ts` AND `themes/dev/editor.js` | ❌ duplicated; renamed to `data-theme-mode` |
| `simpleMode` user preference | `domain/types.ts`, `utils/preferences.ts`, `SettingsModal.tsx` | ⚠️ wrong vocabulary; rename to `themeMode` |
| Editor preview chrome | `themes/dev/editor.{html,js,css}` | ✅ exists |
| Editor → consumer CSS leak | `editor.html:8` reaches `../../src/styles/advanced-themes.css` | ❌ **smoking gun** |

The last row is the smoking gun. The editor cannot work standalone —
it depends on a CSS file that lives in `hadoku-task/src/`. If anyone
clones just the `themes` package, the editor renders the gradient
tokens with no gradient, no effects, and no simple-mode behavior.

## 3. The inconsistencies, in priority order

### 3.1 Advanced CSS lives outside the package (blocker)

`src/styles/advanced-themes.css` defines the entire visual contract
for `data-advanced-theme='beach-day'`: the gradient assembly, the
`.task-app__item` window effect, the shift hover animation, and the
`data-simple-mode` overrides. None of that is in `@wolffm/themes`.
The package ships the *raw stop tokens* but not the recipe that turns
them into a gradient.

That means:
- The editor only works inside the hadoku-task repo.
- Any other consumer (hadoku-site, a future app) gets the
  `--advanced-stop-*` tokens but no `--advanced-gradient`, no
  selector chain, no animation.
- The task-app-specific selectors (`.task-app__item`, etc.) are
  baked into what *should* be a generic theme package.

### 3.2 The naming model is over-engineered

Today's wiring uses **three** attributes to represent **two**
concepts:
- `data-theme` — which family + light/dark
- `data-advanced-theme` — which advanced "package" to apply
- `data-simple-mode` — whether to render advanced visuals

The middle one is redundant: there is a 1:1 map from `data-theme` to
its advanced variant, and that map is already duplicated in two
files (the symptom). A theme name like `light` IS its advanced
identity; the only orthogonal axis is the on/off-ish *mode*.

Collapse to two attributes:
- `data-theme='light'` (unchanged)
- `data-theme-mode='simple' | 'advanced'` (new — replaces both
  `data-advanced-theme` and `data-simple-mode`)

Renames that fall out:
- `simpleMode: boolean` user preference → `themeMode: 'simple' | 'advanced'`
- CSS selectors `[data-advanced-theme='beach-day']` → `[data-theme='light'][data-theme-mode='advanced']`
- API `setSimpleMode()` → `setThemeMode('simple' | 'advanced')`
- delete `ADVANCED_THEME_MAP` entirely from both copies

The string-valued mode also future-proofs for additional modes per
family later (e.g. a hypothetical `'reduced'` or `'high-contrast'`)
without another schema change.

### 3.3 DOM wiring is duplicated between consumer hook and editor

`useTheme.ts` and `editor.js` independently set `data-advanced-theme`
and `data-simple-mode`. They agree today; they won't tomorrow. Today
the editor hard-resets `simpleMode = false` on every theme change
(`editor.js:368`) but the consumer hook reads the user preference and
preserves it. Different mental models, same attributes.

The package should own the wiring. Both the consumer and the editor
should call into a single helper.

### 3.4 No public API for theme mode

`@wolffm/themes` exports `setTheme/getTheme/saveTheme/loadTheme/clearTheme`.
There is no `setThemeMode`, no `getThemeMode`, no upgraded hook.
Consumers re-invent it (which `useTheme.ts` does).

### 3.5 No mode toggle in `task-ui-components`

The user preference exists but there's no shipped component to flip
it. `ThemePicker` shows light/dark family swatches; nothing surfaces
"advanced". The editor has its own inline `<button class="mode-btn">`
pair. The toggle should live **in `ThemePicker`** (not as a sibling
component) since theming is one concept and the toggle is meaningless
when the active theme has no advanced contract.

### 3.6 Advanced CSS hard-codes consumer DOM selectors

`.task-app__item`, `.task-app__item-content`, `.task-app__item-actions`
are hadoku-task DOM. A generic theme package can't know about those.

The fix is theme-owned class hooks the consumer opts into:
- `.hdk-advanced-page` — viewport-fixed gradient background
- `.hdk-advanced-surface` — "window into the gradient" element
- `.hdk-advanced-surface--shift` (and other modifiers) — effect opt-in

The consumer adds the class directly in JSX:

```tsx
<div className="task-app__item hdk-advanced-surface hdk-advanced-surface--shift">
```

### 3.7 Stop tokens are isolated to one theme

Only `[data-theme='light']` defines the 24 `--advanced-stop-*` tokens.
That's correct given only `light` has an advanced contract today —
but it means the contract for "what an advanced theme defines" has
never been formalized. PR 1 collapses the stops, gradient assembly,
color overrides, and effect choice into the same theme block, so
"advanced contract" becomes a clear shape every new advanced theme
fills in.

### 3.8 Editor build is manual

`editor.html` loads `editor.bundle.js` (a hand-rolled IIFE bundle from
`themes/dev/build.js`). There's no watch script — you re-run the
bundler manually after editing `editor.js`. Easy to forget. PR 2 adds
a watch script.

## 4. Proposed architecture

**Flat file layout, no new directories.** The advanced bits for a
theme live in the same block as that theme's base tokens, because
they ARE the same theme.

```
themes/
├── src/
│   ├── style.css          ← 18 theme blocks. Each block that has an
│   │                        advanced contract defines its
│   │                        --advanced-stop-*, --advanced-gradient,
│   │                        color overrides, and effect class
│   │                        selectors INLINE in its own
│   │                        [data-theme='X'] block.
│   ├── advanced.css       ← shared effect kit:
│   │                          .hdk-advanced-surface,
│   │                          .hdk-advanced-page,
│   │                          --shift / --cascade-rich / --sat-rich,
│   │                          [data-theme-mode='simple'] overrides,
│   │                          @media (prefers-reduced-motion).
│   ├── effects.ts         ← per-theme JS effect map (NOT CSS strings):
│   │                          THEME_EFFECTS = {
│   │                            light: { card: 'shift', modal: 'none', ... }
│   │                          }
│   ├── index.ts           ← package API (see §4.1)
│   ├── useTheme.tsx       ← upgraded hook (see §4.2)
│   └── metadata.tsx       ← unchanged
└── dev/
    ├── editor.html        ← imports ../src/style.css AND
    │                        ../src/advanced.css. Nothing else.
    └── editor.js          ← uses package helpers; no duplicate state
```

### 4.1 Package exports

```ts
// existing
export { THEMES, setTheme, getTheme, saveTheme, loadTheme, clearTheme }
export { useTheme }

// new
export { THEME_EFFECTS, hasAdvanced }              // (theme: Theme) => boolean
export { setThemeMode, getThemeMode, saveThemeMode } // 'simple' | 'advanced'
export type { ThemeMode }
```

`hasAdvanced(theme)` is a simple key lookup against `THEME_EFFECTS` —
no DOM, no `getComputedStyle`.

### 4.2 Upgraded `useTheme` hook

```ts
const {
  theme, setTheme,
  themeMode, setThemeMode,        // 'simple' | 'advanced'
  hasAdvanced                      // bool — UI uses to show/hide toggle
} = useTheme()
```

The hook owns all four pieces of state and applies all attributes.
The hadoku-task `useTheme.ts` shrinks to just the bits that are
app-specific (experimental themes, mount-param priority,
auto-switch on system preference).

### 4.3 Class hooks (in `advanced.css`)

```css
.hdk-advanced-page {
  background: var(--advanced-gradient);
  background-attachment: fixed;
}

.hdk-advanced-surface {
  position: relative;
  overflow: hidden;
  background: var(--advanced-gradient);
  background-attachment: fixed;
}

.hdk-advanced-surface--shift::after { /* …shift overlay… */ }
.hdk-advanced-surface--shift:hover::after { /* hover state */ }

/* Simple mode disables the gradient kit */
[data-theme-mode='simple'] .hdk-advanced-page {
  background: var(--color-bg);
}
[data-theme-mode='simple'] .hdk-advanced-surface {
  background: var(--color-bg-card);
}
[data-theme-mode='simple'] .hdk-advanced-surface::after { display: none; }

@media (prefers-reduced-motion: reduce) {
  .hdk-advanced-surface::after { transition: none; }
}
```

Per-theme blocks in `style.css` only define the gradient and any
color overrides:

```css
[data-theme='light'] {
  /* simple-mode colors (existing) */
  --color-primary: #2563eb;
  /* …etc… */

  /* advanced contract */
  --advanced-stop-1-l: 0.82; /* …etc… */
  --advanced-gradient: linear-gradient(135deg,
    oklch(var(--advanced-stop-1-l) ...) 0%,
    /* …8 stops… */
  );
}
```

The consumer's job is **add the class to the right element**:

```tsx
<div className="task-app__item hdk-advanced-surface hdk-advanced-surface--shift">
```

No `.task-app__item` selectors anywhere in the theme package.

### 4.4 Per-theme effect map — JS, not CSS strings

A future `<Card>` component (Path B in §7) needs to know which
effect modifier to apply for the active theme. Two options:

- **CSS custom-prop strings** (rejected): `--advanced-effect-card: 'shift';`
  read via `getComputedStyle().getPropertyValue()`. Browsers return
  the literal text — sometimes wrapped in quotes, sometimes with
  leading whitespace, varies by engine. Components would need
  cleanup code per browser.
- **Typed JS export** (accepted):

```ts
// themes/src/effects.ts
export type ThemeEffectMap = {
  card: 'shift' | 'cascade-rich' | 'sat-rich' | 'none'
  modal: 'shift' | 'cascade-rich' | 'sat-rich' | 'none'
  button: 'shift' | 'cascade-rich' | 'sat-rich' | 'none'
}

export const THEME_EFFECTS: Record<string, ThemeEffectMap> = {
  light: { card: 'shift', modal: 'none', button: 'none' }
  // 'cyberpunk-dark': { card: 'cascade-rich', modal: 'shift', button: 'none' }
}
```

No DOM read, no parsing, type-safe, works across frameworks.
`hasAdvanced(theme)` is `theme in THEME_EFFECTS`.

## 5. Migration plan — 2 PRs

### PR 1 — Consolidate the package: own the CSS, the API, and the wiring

Single atomic change. Touches both packages because deleting the
duplicate state in the consumer is required for the new package state
to be authoritative — splitting would leave the system in a broken
intermediate.

**In `@wolffm/themes`:**
- Add `themes/src/advanced.css` with the shared kit (`.hdk-advanced-surface`,
  modifiers `--shift / --cascade-rich / --sat-rich` ported from
  `editor.css`'s `shimmer-*` classes, `[data-theme-mode='simple']`
  overrides, reduced-motion).
- Inline beach-day's gradient stops, gradient assembly, and color
  overrides into the `[data-theme='light']` block in `style.css`.
  Selectors switch from `[data-advanced-theme='beach-day']` to
  `[data-theme='light'][data-theme-mode='advanced']`.
- Replace `.task-app__item*` selectors with `.hdk-advanced-surface*`
  in the shared kit.
- Add `themes/src/effects.ts` exporting `THEME_EFFECTS` and
  `hasAdvanced`.
- Add `setThemeMode/getThemeMode/saveThemeMode` to `themes/src/index.ts`.
- Upgrade `useTheme` to manage `themeMode` and `hasAdvanced`.
- Add `"./advanced.css": "./src/advanced.css"` to `package.json` exports.

**In `hadoku-task` (consumer):**
- Delete `src/styles/advanced-themes.css`.
- Replace `@import './advanced-themes.css'` in `src/styles/style.css`
  with `@import '@wolffm/themes/advanced.css'`.
- Delete `ADVANCED_THEME_MAP` from `src/app/themeConfig.tsx`.
- Migrate `simpleMode: boolean` → `themeMode: 'simple' | 'advanced'`
  in `domain/types.ts`, `utils/preferences.ts`,
  `components/modals/SettingsModal.tsx`. Add a one-time read-side
  migration: if saved prefs have `simpleMode`, derive
  `themeMode = simpleMode ? 'simple' : 'advanced'` and drop the old
  key.
- Strip the duplicated effect blocks from `src/hooks/useTheme.ts`
  (the `data-advanced-theme` and `data-simple-mode` setters at lines
  159–201). The package hook owns it now.
- Add `hdk-advanced-surface` / `hdk-advanced-page` classes to JSX
  where the gradient should appear (page container + task cards).

**In `themes/dev/editor.{html,js,config.js}`:**
- Delete `<link rel='stylesheet' href='../../src/styles/advanced-themes.css'>`.
- Add `<link rel='stylesheet' href='../src/advanced.css'>`.
- Replace local `setMode` and attribute writes with `setThemeMode`
  from the package.
- Rename "Basic" button label → "Simple" to match the attribute and
  preference names.
- Delete the duplicate `ADVANCED_THEME_MAP` from `themes/dev/config.js`.

**Validation (real users, real prefs):**
- User on light theme, default prefs → still sees the gradient + shift
  hover (now via `data-theme-mode='advanced'` instead of
  `data-advanced-theme='beach-day'`). Pixels identical.
- User who had toggled `simpleMode: true` in settings → migration
  produces `themeMode: 'simple'`, sees flat colors as before.
- User on any non-light theme → `hasAdvanced === false`, no toggle
  visible, flat rendering as today.
- Editor renders identically to consumer.

### PR 2 — ThemePicker mode toggle + a second advanced theme

Two pieces, one PR, because the toggle is meaningless without a
second theme to prove the architecture isn't `light`-shaped.

**In `task-ui-components`:**
- Extend `ThemePicker` with a built-in mode toggle. Renders only when
  `hasAdvanced(currentTheme)`. Visual: a small two-state pill at the
  right edge of the picker bar ("Simple" / "Advanced"), styled like
  the existing light/dark sub-toggle. Reads `themeMode` and
  `setThemeMode` from `useTheme`. No new component name — keep
  everything theme-related inside `ThemePicker`.

**In `@wolffm/themes`:**
- Add an advanced contract to a dark family theme. Recommend
  `cyberpunk-dark` with the `cascade-rich` effect — different mood,
  different effect, different stops, proves color-overriding works on
  a dark base. Define inline in the existing `[data-theme='cyberpunk-dark']`
  block in `style.css`. Add to `THEME_EFFECTS` in `effects.ts`.
- Add the `dev` watch script: `pnpm --filter @wolffm/themes editor`
  runs the IIFE bundler in watch mode + `save-server.js`.

**In `hadoku-task`:**
- No changes beyond consuming the new ThemePicker behavior.

**Validation:**
- Toggle is visible on `light` and `cyberpunk-dark`, hidden on every
  other theme.
- Switching `light → cyberpunk-dark` while in advanced mode flips to
  the cascade-rich effect cleanly, no FOUC.
- Editor renders both new themes correctly with no manual rebuild.

## 6. Decisions (locked)

| # | Decision | Implication |
|---|---|---|
| 1 | Vocabulary: **"Advanced" / "Simple"**. Mode is `themeMode: 'simple' \| 'advanced'`. Attribute is `data-theme-mode`. Editor button labels match. | Rename `Basic` → `Simple`, replace `simpleMode` boolean, delete `data-simple-mode` and `data-advanced-theme`. |
| 2 | `themeMode` is **global** (one switch for the app). | No per-theme override needed. |
| 3 | Each advanced theme **shows off different effects**. Variety is the goal. | Package needs a **kit of effect classes** (`--shift`, `--cascade-rich`, `--sat-rich`, future ones), not just one. Each theme picks via `THEME_EFFECTS`. |
| 4 | Keep the **8-stop** editor — complex colors are a feature. | No simplification of `GRADIENT_VARS`. |
| 5 | Advanced themes **define their own color set**. | A `[data-theme='light']` block in advanced mode can override `--color-primary`, `--color-bg`, etc. — not just gradient stops. The base colors apply when `themeMode='simple'`. |
| 6 | **Per-component effect tuning** is required. | Effect classes go on individual elements. A theme might say cards = `--shift`, modals = none, buttons = none. |
| 7 | **No "advanced theme" naming.** A theme name like `light` IS its advanced identity. No `beach-day`, no `ADVANCED_THEME_MAP`. | One less attribute, one less mental model, two fewer files of duplicate state. |
| 8 | Goal: **drop-in across any app**. Path B (themed primitives) on the table later, not now. | See §7. |

## 7. Path A vs Path B

### Path A — Class-hook contract (ship now)

Package exposes `.hdk-advanced-surface`, `.hdk-advanced-page`, and
effect modifiers. Consumers add the classes in their JSX:

```tsx
<div className="task-app__item hdk-advanced-surface hdk-advanced-surface--shift">
```

- ✅ Tiny package, tiny refactor, framework-agnostic
- ✅ Per-component tuning is natural
- ❌ Consumer has to know the class names
- ❌ A theme can't enforce "modals are flat, cards shimmer" — the
  consumer chooses

### Path B — Themed primitive components (later)

`task-ui-components` exports `<Surface>`, `<Card>`, `<Modal>`,
`<Button>` etc. Each one reads `THEME_EFFECTS` (the JS map from §4.4)
and applies the right modifier class internally. Consumer writes:

```tsx
<Card>...</Card>   // automatically gets the right effect
```

- ✅ Consumers think zero about theming
- ✅ Theme can enforce per-component effect choice
- ❌ Bigger refactor — every `<div className="card">` migrates
- ❌ React-specific

### Recommendation

**Path A first** — that's where the broken thing is (the package
literally doesn't ship a working advanced theme today). Once Path A
lands and 2-3 advanced themes exist, Path B becomes a refactor of
`task-ui-components` only — the theme package contract doesn't
change. Each `<Card>` just becomes a
`<div className="hdk-advanced-surface ...">` internally.

Path B is **deferred**. Not in the migration plan above. Revisit
once we have at least 3 advanced themes shipped and have a real feel
for what effect variety looks like.
